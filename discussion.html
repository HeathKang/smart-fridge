MVP DECISIONS

先解决食材过期

讨论稿 · 等待共同决策

目标：让家里人知道什么该先吃，并愿意持续更新冰箱里的食材。

01 / 买回来

快速记一笔

支持订单截图批量识别；也可逐个添加食材，用图片识别或手动填写。识别结果入库前均可修改确认。

02 / 打开冰箱

先看到需要处理的

首页按已过预计日期、近期要吃、还能存放排序。聚焦叶菜、水果、鲜肉和剩菜等容易被忘记的东西。

03 / 吃完之后

顺手更新

提供「吃完了」和「还剩一些」，避免要求每次输入精确克数。提醒汇总成每天一次，帮助形成习惯。

建议的第一版范围

订单截图批量录入 + 单个食材图片或手动录入，结合临期排序与吃完移除。以送达当天为起点，由模型结合食材及储存方式估算一般建议食用日期；入库前可修改，包装上的实际日期优先。图片识别、估算、送达日期、数量和通知尚未实现，上方为交互概念。

需要一起决定的 3 个问题

已决定：订单截图批量录入；单个食材支持图片或手动录入；从送达当天开始估算，日期可手动修改。
待决定：截图识别后是否默认只勾选易过期食材？冷藏、冷冻等储存方式如何选择？

日期是预计食用期限，不代表食材一定安全或已经变质；包装日期和食材实际状态都需要参考。

TECHNICAL DIRECTION

技术选型 · 待 Review

面向 QNAP 家庭内网

先专注家庭内网的单实例部署，保持组件少，保留未来替换模型和数据库的空间。

整体结构

手机浏览器 / 电脑 → Web 页面 → FastAPI 应用 → SQLite（持久化目录）
　　　　　　　　　　　　　　　　　↘ 可配置的视觉 LLM 服务
QNAP 上运行应用容器和本地数据卷；模型请求通过网络发送到配置的 API 服务。

01 / 前端

响应式 Web + React / TypeScript

手机优先，浏览器打开即可使用，无需应用商店。支持选择或拍摄图片；MVP 暂不依赖原生 App 和离线能力。

权衡：需要前端构建流程；如果团队更熟悉其他框架，也可替换。

02 / 应用服务

Python + FastAPI

提供库存、图片识别与日期估算接口，由服务端调用模型并保管密钥。前端静态文件可由同一应用提供。

权衡：需维护 Python 依赖和数据库迁移；适合快速实现模型调用。

03 / 数据

SQLite + 本机持久化卷

家庭低并发先用单文件数据库，随容器升级保留；定期使用 SQLite 备份机制备份并验证恢复。

边界：数据库放在应用所在机器的本地文件系统，避免通过网络共享文件直接访问；写入并发增长再评估 PostgreSQL。

04 / 图片与模型

服务端模型适配层

使用通用 OpenAI 兼容 API；服务端配置 Base URL、API Key 和模型名称。订单截图和食材图片由支持视觉输入的模型识别，返回候选；用户确认后才写入。估算日期记录依据、储存方式和人工修改。

权衡：兼容接口不保证所有供应商的视觉输入或结构化输出完全一致，需要验证所选模型；外部调用有费用、延迟和隐私影响，手动录入始终可用。

05 / 部署

Docker Compose

QNAP 上使用 Docker Compose 运行应用，使用持久化数据卷和环境变量配置。按 NAS 的 CPU 架构构建兼容镜像。

权衡：QNAP 已确认可用 Docker；具体 CPU 架构与系统版本部署前确认。

06 / 访问方式

家庭内网，无需账号

先在可信的家庭内网使用，不实现注册、登录和多用户权限；局域网内的使用者共享同一份冰箱数据。

权衡：内网内能访问服务的设备都可以查看和修改数据；部署时避免公网端口映射。

数据与隐私的默认方案

截图可能包含姓名、地址和电话：上传前提示并允许裁剪；服务端仅为识别临时处理，默认不长期保存原图、不将其写入日志。若使用外部模型，需明确告知图片会发送给所选服务商。密钥只放服务端配置，不放前端或代码仓库。

这轮建议重点决定

已决定：仅部署 QNAP 家庭内网，使用 Docker Compose；不做账号控制，共享家庭库存；模型接入通用 OpenAI 兼容 API。暂不考虑 VPS 和微信小程序。
部署前确认：QNAP CPU 架构、系统版本及所选 API 的视觉能力。

参考：SQLite 适用场景 · SQLite 网络文件系统注意事项 · FastAPI 容器部署 · Docker Compose。以上为建议选型，尚未实现。
